§8–9

Expected points

This stage takes the minutes scenarios, the per-90 rates and the fixture adjustment, and turns them into FPL points. It adds the points from each part of the game, then sums fixtures into one total per gameweek and per horizon.

§8Expected points (xP) components

In short: a player's xP for one fixture is the sum of nine parts, such as appearance, goals and clean sheets, each priced with the FPL points table.

estimate Every xP value is a model result, not a fact. It turns past and current stats (evidence, fact) into per-90 rates and minutes (estimate), then into points.

Two scenarios per fixture

The selection model (§4.5) gives two ways the player can feature. The code computes every component once for each way, then weights the results by how likely each way is.

Start scenario

The player starts. weight is the chance of this scenario, and the scenario carries its own expected minutes.

Cameo scenario

The player plays as a substitute. It has its own weight and its own expected minutes.

weight = probability // of that scenario minutesShare = clamp(minutes, 0, 90) / 90

Each component below adds weight times its own term, once per scenario.

§8.1Appearance

In short: 1 point for playing, 2 points for playing 60 minutes or more.

appearance += weight * (minutes >= 60 ? 2 : 1) // 1 for playing, 2 for 60+ min

§8.2Goals

In short: expected goals, converted for the position, scaled by minutes and the fixture, times the points for a goal.

goals += weight * xgRate * GOAL_CONVERSION[position] * minutesShare * attackMultiplier * GOAL_POINTS[position]
GOAL_POINTS = { GK: 10, DEF: 6, MID: 5, FWD: 4 }

Goalkeepers are the exception. Their goals component is always zero: 0 goals in about 9,700 walk-forward GK rows in 2023/24–2025/26, and their xG prior is 0.

attackMultiplier comes from the fixture adjustment (previous page).

A midfielder: weight 0.8, xgRate 0.40 per 90, conversion 0.981, a full 90 minutes (minutesShare 1), attackMultiplier 1.0, 5 points per goal. All made up.

0.8 * 0.40 * 0.981 * 1 * 1.0 * 5 = 1.5696

§8.3Assists

In short: expected assists, converted for the position, scaled the same way, times 3 points.

assists += weight * xaRate * ASSIST_CONVERSION[position] * minutesShare * attackMultiplier * 3

These are two separate facts. A defender's chances are set-piece headers, and they convert at 0.70, where a midfielder or forward converts at close to 1.0. And FPL pays more assists than xA predicts: it pays for the final pass whatever happens to the shot, so a forward earns 2.11 assists per xA.

What the table leaves out on purpose

A larger set of factors scores better on the backtest: RMSE −0.0074, with the paired interval excluding zero, against no measurable gain for the factors above. Those larger factors also absorb a second effect, which is the model overstating a midfielder's xG rate by 20%. They are not shipped, because tests/core/calibration.test.ts catches what they really are.

Given exact rates, they under-pay midfielders by 0.178 points and over-pay forwards by 0.215. That pushes the positional spread to 0.393, against a guard of 0.35. A rate error is not a scoring rule, so it does not belong in one. The table above holds the guard at 0.284.

OpenThe rate error is real and unfixed. §6.3.1 is where it lives. Shrinking a player's own anchor toward the pool rate by its sample size was worth −0.0237 RMSE in testing, which is more than anything else measured so far. It barely moves the bias, so the cause is regression to the mean, not noise. It stays open.

To re-derive any of this, run npx tsx scripts/backtest/fit-conversions.ts.

§8.4Clean sheets

In short: a clean sheet pays only if the player reaches 60 minutes.

cleanSheets += weight * cleanSheetProbability * CLEAN_SHEET_POINTS[position] // only if the player reaches 60 minutes CLEAN_SHEET_POINTS = { GK: 4, DEF: 4, MID: 1, FWD: 0 }

§8.5Goals conceded (GK/DEF only)

In short: a goalkeeper or defender loses 1 point for every 2 goals conceded while on the pitch.

This is a threshold rule, so a straight average would give the wrong answer. The code sums over a Poisson count of goals instead, and takes the expected value of the rounded-down half.

goalsConceded -= weight * E[ floor(expectedGoalsAgainst * minutesShare / 2) ]

E[floor(X / d)] uses a Poisson(expectedGoalsAgainst * minutesShare) distribution.

lib/projections/distributions.ts · expectedFloorDivision

§8.6Saves (GK only)

In short: 1 point per 3 saves, with the save rate scaled by how many goals the opponent is expected to score.

The same sum over a distribution applies. The environment factor stays between 0.7 and 1.4.

savesEnvironment = clamp(expectedGoalsAgainst / 1.35, 0.7, 1.4) saves += weight * E[ floor(savesRate * minutesShare * savesEnvironment / 3) ]

§8.7Defensive contributions

In short: 2 points once a player's count of defensive actions reaches 10 (DEF) or 12 (MID, FWD); goalkeepers get none.

The code needs the chance of reaching the threshold, not a share of it.

defensiveContribution += weight * 2 * P(count >= threshold)

P(count >= threshold) uses a negative binomial with mean defContRate * minutesShare and dispersion = 8. Match-by-match counts spread out more than a Poisson allows.

§8.8Bonus

In short: bonus points follow the player's regressed bonus rate and expected minutes; only GK and DEF carry the fixture's attack multiplier.

bonusMultiplier = position in {GK, DEF} ? adjustment.attackMultiplier : 1 bonus += weight * bonusRate * minutesShare * bonusMultiplier

MID and FWD use a flat bonus rate.

Backtest evidence

The Tier C comparison cut MID/FWD whole-xP RMSE by 0.0051 (95% gameweek-cluster interval −0.0081 to −0.0022). It used 11,947 player-fixtures from 2024/25–2025/26.

CaveatBonus-only RMSE is still unresolved. The result supports the change to total points, not a claim of better bonus forecasts. See scripts/backtest/results/tier-c-bonus.md.

§8.9Cards

In short: a yellow costs 1 point and a red costs 3, each weighted by the chance it happens in the minutes played.

yellowChance = 1 - exp(-yellowRate * minutesShare) redChance = 1 - exp(-redRate * minutesShare) cards -= weight * (1 * yellowChance + 3 * redChance)

A booking either happens or it does not. That makes this a probability, not a rate times minutes, and it stops a full match from implying more than one card. The code adds yellows and reds separately. A red that follows a second yellow is rare (0.005 per 90 at its highest), so the code does not model the overlap.

yellowRate and redRate are the player's own rates from §6.3. They use a prior weight of 40 matches and ceilings of 0.8 and 0.1 per 90. evidence The position priors are measured, not assumed. This table covers every 2025/26 appearance:

League-wide that is −0.135 points per appearance. It differs by position: a defender loses about twice what a forward does. Leaving cards out flattered defenders, and held midfielders, against the forwards they compete with.

Priors in code, and what the cards term fixed

No forward was sent off in the sample, so their red prior is a floor and not the observed zero. The code rounds the red priors to GK 0.001, DEF 0.008, MID 0.005 and FWD 0.002.

Adding this term moved overall bias from +0.174 to +0.045 points per appearance. It moved midfielders from +0.175 to +0.001. Both figures use a per-player anchor (npx tsx scripts/backtest/anchor.ts).

§8.11Breakdown display

In short: the breakdown view shows one gameweek's xP split into its parts and adds no maths of its own.

  • packComponents sends each fixture's components as nine numbers rounded to 0.01, in the fixed order of BREAKDOWN_COMPONENT_KEYS: appearance, goals, assists, cleanSheets, goalsConceded, saves, defensiveContribution, bonus, cards. It leaves out penalties and total. unpackComponents rebuilds the object and recomputes total from the parts. The order is the format, so new keys go at the end.
  • gameweekBreakdown sums the components of every fixture in the gameweek (a double gameweek reports matches = 2). It returns null when the player has no fixture or no components. A row is hidden only when the position cannot score it and its value is zero, so the rows shown always add up to the total shown.
  • Each row cites the player's recorded per-90 figures for this season and last. A sample under 90 minutes reads "not enough minutes yet" in place of a number.

§9Aggregation: nextGW, next3, next5, next10, value

In short: xP sums per gameweek first, then over the next 1, 3, 5 or 10 gameweeks, and value divides the 5-week total by the price in millions.

projectPlayer projects every upcoming fixture, from currentGameweek out to fixtureHorizon (by default, the season's remaining weeks), and then sums.

Value

valueNext5 = next5 / (priceTenths / 10)

fact The price is the live FPL price, kept in integer tenths. Dividing by 10 turns it into millions only for this step.

With next5 = 17.9 from the strip above and a made-up price of 75 tenths (£7.5m):

17.9 / (75 / 10) = 17.9 / 7.5 = 2.39 // rounded to two places

factors builds the list of reasons the interface shows: expected minutes, average fixture difficulty, confidence and position model. It is for display only.
