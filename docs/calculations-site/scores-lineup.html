§10–14

Risk, value & weekly lineup

This stage takes each player's expected points and availability. It scores risk, confidence, value and utility, then builds the weekly XI, bench, captain and total.

§10Risk score

In short: a 0 to 100 score where higher means a less safe pick. estimate

Four parts add up. The maximum each part can add is fixed: minutes 38, availability 35, sample 17, confidence 10.

minutesRisk = expectedMinutes === undefined ? 25 : clamp((90 - expectedMinutes) / 90, 0, 1) * 38 availabilityRisk = (1 - availability(player)) * 35 sampleRisk = clamp(1 - sampleMinutes / 1800, 0, 1) * 17 confidenceRisk = LOW ? 10 : MEDIUM ? 5 : 0 riskScore = round(clamp(minutesRisk + availabilityRisk + sampleRisk + confidenceRisk, 0, 100))

lib/projections/metrics.ts · calculateRiskScore

A player with 72 expected minutes, a 75% chance of playing, 900 sample minutes and MEDIUM confidence (made-up numbers):

  • minutesRisk = (90 - 72) / 90 * 38 = 7.6
  • availabilityRisk = (1 - 0.75) * 35 = 8.75
  • sampleRisk = (1 - 900 / 1800) * 17 = 8.5
  • confidenceRisk = 5
  • riskScore = round(7.6 + 8.75 + 8.5 + 5) = round(29.85) = 30
Score of 100No projected minutes, a 0% chance of playing, no sample, and low confidence.
Inputs and the availability helper

sampleMinutes is historical.minutes ?? current.minutes. availability here is the simpler helper in lib/projections/metrics.ts: chanceOfPlaying / 100 when FPL gives a percentage. Otherwise it is 0.25 for an unavailable status (i, s, u, n), 0.75 for doubtful (d), else 1.

When expectedMinutes is missing, minutesRisk is a flat 25.

§13Utility value

In short: utility is a ranking score for the optimizer. It is not xP. estimate

Utility starts from xP and scales it by minutes, confidence, availability and the chosen risk mode. SAFE and BALANCED always scale it down; AGGRESSIVE can lift it slightly above xP.

The four weights inside the bracket add to 1. Minutes, confidence and availability each take part of the 1; 0.62 is the share every player keeps.

projection = horizonValue(player, horizon) minutes = expectedMinutes(player) / 100 confidence = confidenceWeight(projection.confidence) // §11 availability = 1 - availabilityRisk(player) riskMultiplier = SAFE ? 0.72 : AGGRESSIVE ? 1.08 : 0.90 utility = projection * (0.62 + 0.16*minutes + 0.12*confidence + 0.10*availability) * riskMultiplier

Projection 5.0, expected minutes 80, HIGH confidence, full availability, BALANCED (made-up numbers):

  • bracket = 0.62 + 0.16*0.8 + 0.12*1 + 0.10*1 = 0.968
  • utility = 5.0 * 0.968 * 0.90 = 4.356
availabilityRisk and windowUtility

availabilityRisk (lib/analysis/context.ts) is its own helper: status i/s adds 0.75, d/u adds 0.35, and chanceOfPlaying adds max(0, 1 - chance/100) * 0.65, capped at 1.

windowUtility scores an explicit planning window [gameweek, gameweek + horizon - 1] rather than always starting at the live gameweek:

windowValue = sum over g in [gameweek, ..., gameweek + horizon - 1] of gameweekValue(player, g) windowUtility = windowValue * utilityScale(player, risk)

gameweekValue returns the fixture-projected points for that gameweek. Double gameweeks sum, and blank gameweeks score zero. Multi-gameweek plans and the exact optimizer use this.

§14.1Per-player weekly metrics

In short: each player gets points and minutes for one gameweek. estimate

basePoints returns a player's points for one gameweek:

  1. With fixture-level projections for that gameweek, sum their expectedPoints. A blank gameweek returns 0.
  2. With a fixture schedule but no entry for this gameweek, return 0. It never reuses nextGW from another week.
  3. Otherwise use projection.nextGW, then pointsPer90 * minutes / 90.

minutes sums the fixture expectedMinutes for the gameweek, each clamped 0 to 90.

lib/squad/weeklyLineup.ts · basePoints, minutes

§14.2Probability did not play (pDNP)

In short: the chance a player gets no minutes this gameweek. estimate

Rules run top to bottom; the first match wins.

if (fixture schedule exists and no fixture this gameweek) → 1 if (fixtures exist but 0 minutes) → 1 if (status is i, u, n or s) → 1 if (selection.noAppearanceProbability is finite) → clamp(noAppearanceProbability, 0, 1) // fallback, for a player without a selection model: availabilityRisk = status d ? 0.5 : 0 availabilityRisk = max(availabilityRisk, 1 - chanceOfPlaying/100) minutesRisk = clamp((45 - minutes) / 45, 0, 1) pDNP = clamp(availabilityRisk * 0.75 + minutesRisk * 0.25, 0, 1)

lib/squad/weeklyLineup.ts · probabilityDidNotPlay

In the appenrichPlayersWithHistory gives every player a selection, so pDNP is the selection model's no-appearance probability (§4.5). The 0.75 / 0.25 fallback runs only for a player built without one, such as in a test.

§14.4Selecting the XI and risk modes

In short: keep the XIs within 0.25 points of the best, then break the near-tie by risk mode.

Each candidate has three scores: projectedXI (sum of starter points), risk (sum of pDNP) and minutes (sum of minutes). The near-equal window of 0.25 points keeps candidates whose projected XI is within 0.25 of the best. compareCandidates then picks the winner:

SAFE

Minimize total risk (pDNP).

BALANCED

Maximize total minutes.

Remaining ties: highest projected XI, then lowest risk (not in AGGRESSIVE), then most minutes, then id. The id step makes the result the same every time.

lib/squad/weeklyLineup.ts · compareCandidates

§14.5Bench order and autosubs

In short: the bench order with the highest expected autosub value wins.

The bench is one GK plus three ordered outfield substitutes. expectedAutosubValue computes the expected points a bench order recovers, across all appearance masks:

  • Goalkeeper: P(starting GK out) * P(bench GK plays) * benchGK.points.
  • Outfield: for each starting and bench appearance state, substitutes play in bench order for absent starters only where FPL formation rules still hold (legalFormation). Each one adds the substitute's points.

lib/squad/weeklyLineup.ts · expectedAutosubValue, legalFormation

§14.6Captain and vice-captain

In short: the captain has the most points; the vice-captain has the most points weighted by the chance to play.

Captain

The starter with the highest points. Ties go to the lowest pDNP, then id.

Vice-captain

The highest points * (1 - pDNP) among the rest.

lib/squad/weeklyLineup.ts · captainPair

§14.7Weekly totals

In short: total = starters + armband bonus + expected autosub value.

projectedXI = sum of starter points captainBonus = (1 - pDNP_C) * points_C + pDNP_C * (1 - pDNP_V) * points_V autosubValue = expected autosub value (§14.5) projectedTotal = projectedXI + captainBonus + autosubValue

expectedCaptainBonus pays the armband's extra points: the captain's when the captain plays, else the vice-captain's when the vice-captain plays. The tree shows the two paths.

Captain: points 8, pDNP 0.1. Vice-captain: points 6, pDNP 0.2 (made-up numbers).

  • captainBonus = 0.9 * 8 + 0.1 * 0.8 * 6 = 7.2 + 0.48 = 7.68

Chips

Triple Captain (3xc)

captainBonus is doubled, so the armband pays two extra multiples.

Bench Boost (bboost)

All 15 players score. projectedXI sums all 15 and the captain and vice-captain come from all 15. autosubValue is 0 because no one comes off the bench.

Free Hit and Wildcard change the squad, not the lineup scoring (§19.3).

§14.8Projection fingerprint

In short: a short hash tells the app when a saved lineup no longer matches the projections.

The fingerprint is an FNV-1a hash of the gameweek plus every player's basePoints and pDNP (to 3 decimals). A stale fingerprint on a saved lineup gives a warning rather than a silent overwrite.
