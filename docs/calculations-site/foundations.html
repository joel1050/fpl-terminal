§1–3

Inputs & team strength

This stage fixes the units, sorts every input into fact, evidence or estimate, and rates each club. It hands on clean player data and attack and defence strength ratios for each club.

§1Units and conventions

In short: every number in the app uses one fixed scale, so values from different stages fit together.

105

Money

Integer tenths of a million pounds. 105 means £10.5m. Convert only for display: priceTenths / 10.

0–90

Minutes

Always on a 0–90 scale for a single fixture.

0–1

Probabilities

A chance of 0.25 means one in four.

per 90

Rates

xG, xA, bonus, saves and defensive contributions are always per 90 minutes.

mean

xP

Expected points are an average expectation, never a simulated sample.

1 | 3 | 5 | 10

Horizons

Gameweeks ahead. They count distinct gameweeks, not fixtures (see §9).

§2Inputs and normalization

In short: the app turns live FPL data into one clean model and keeps facts, evidence and estimates apart.

fact

Live data straight from the FPL API: price, ownership, status, fixtures, season totals.

evidence

Past results and published labels: last season's match data, RotoWire lineups, historical ClubElo.

estimate

Model output: fixture difficulty, projections, risk and confidence. Each traces back to its inputs.

§2.2Fixtures fact and difficulty estimate

In short: the app ignores FPL's own difficulty labels and rates each fixture from the Elo gap between the two clubs.

Club Elo snapshotdata/generated/club-elo.json
→
Match clubsFPL short name to ClubElo code
→
Elo gapE_opp − E_own
→
Difficulty1 (easy) to 5 (hard)

FDR is venue-agnostic by design. Venue lives in the attack multiplier (1.102 / 0.898) and in the clean-sheet path (§7). FDR rates only the Elo gap.

difficulty = clamp(round(3 + (E_opp - E_own) / 300), 1, 5) exactDifficulty = clamp(3 + (E_opp - E_own) / 300, 1, 5)

Both use 300 Elo per step. The screen shows the whole number. The projection uses the exact value, fraction included.

Club ratings are made up. Own Elo 1900, opponent Elo 2100.

  1. Gap = 2100 − 1900 = 200.
  2. exactDifficulty = 3 + 200 / 300 = 3.667.
  3. difficulty = round(3.667) = 4.

A gap of +600 or more gives 5. A gap of −600 or less gives 1. A missing club rating gives 3.

Club matching and safeguards
  • normalizeFixtures and normalizePlayerDetail replace FPL's labels with the ClubElo snapshot. The upstream team_h_difficulty, team_a_difficulty and player-detail difficulty fields stay in the schemas for transport, but the app ignores them. Both functions take an optional snapshot, so a test can rate fixtures against one it builds.
  • Short names match ClubElo's three-letter codes. The source is not unique here: its England table lists both Stoke and Stockport as STO. A code held by two clubs names neither, so the lookup returns nothing instead of the higher-rated club.
  • BHA, MUN and NFO have no matching code. FPL_TO_CLUB_ELO_SLUG maps them by slug (Brighton, ManUnited, Forest). Snapshot slugs are unique, so a mapped club cannot be displaced.
  • An unresolved club returns neutral difficulty 3. It never falls back to FPL.
  • npm run data:elo refuses to write a snapshot that cannot rate a current team. It names each team and the repair: a shared code, a code no club carries, or a mapped slug ClubElo has since renamed.
  • The refresh parses exact decimal rows in ClubElo's vegaJson, merges the full England ranking so clubs outside the chart's top 25 stay available, and writes the checked snapshot in one atomic step. Where two exact rows share a code, the merge keeps the ranking's own rounded Elo rather than attach one club's rating to another's row.
  • The snapshot is a static import, so it cannot change inside one process and stays out of the projection cache key. Its age does change. enrichBootstrapWithProjections recomputes the age on every call and reports clubElo next to lineups: snapshotDate is the day ClubElo rated the clubs, fetchedAt the day the file was downloaded, ageSeconds how long ago that was. Elo feeds every fixture difficulty, so a snapshot left alone drifts.
Backtest evidence for 300 Elo per step

The Tier C walk-forward experiment picked 300 on 2023/24. On held-out 2024/25–2025/26 it cut team-xG multiplier RMSE by 0.00307 against 150 (95% gameweek-cluster interval −0.00514 to −0.00107). Historical Elo was a result-derived proxy, not archived ClubElo, so this supports the divisor on that proxy only.

§2.2.1Historical ClubElo for backtests evidence

In short: a backtest rates a past fixture with the last Elo published before that day, and never with a later one.

Rule

For a fixture on date d, use the latest point with point.date < d. Same-day points are out, because the chart records post-match ratings.

No substitutes

A missing earlier value fails the lookup. Future values and synthetic ratings do not fill in.

Rating age

The code records the age, since a summer break can leave the last value months old. In the committed fixture panel the 95th-percentile lag is 15 days and the maximum is 107 days.

Source and limits
  • Public club pages embed dated Date/Elo rows in their vegaJson chart data. clubelo-history.ts fetches and checks these rows. It does not fill past ratings from the current ranking.
  • The dated CSV API was not reachable during this extraction. The public chart data covered all 25 clubs and 1,140 fixtures in 2023/24–2025/26. The archive records each club's source URL identity, retrieval time and raw dated rating values.
  • Chart values fetched today are evidence for retrospective tests. They do not copy the whole FPL input state at an old deadline.
  • Production still reads the committed current snapshot. Fetching the historical archive does not refresh that snapshot or change live projections.

§2.4RotoWire evidence

In short: RotoWire says who will start or who is out, and the app uses a team sheet only for the fixture it belongs to.

STARTER

lineupStatus is PREDICTED or CONFIRMED.

UNAVAILABLE

availabilityStatus is QUES, OUT or SUS.

Names map to FPL player ids in three steps: confirmed mapping, exact name, unique fallback. The app rejects ambiguous or unmapped records.

How a team sheet gets used
  • At selection time, records group by their source fixture. The app keeps a group only when both mapped teams match the player's target PlayerFixture in the projected gameweek.
  • Once that fixture ends, its official FPL minutes feed the current-season role history. The old team sheet cannot raise a future fixture's start probability.
  • An omitted team does not count as covered. It stays on the historical and current-season estimate.

§3Team strength estimate

In short: each club gets an attack and a defence ratio around 1.0, built in three layers that each nudge the one before and none overrides it.

1. Preseason consensus (§3.1)Hand-set tiers 1–5 per club, turned into ratios from 0.84 to 1.16.
2. Normalized by source (§3.2)Each value divided by the league average of its own source group.
3. Blended with in-season xG form (§3.3)The prior mixes with what the club has done this season, with more weight as matches pile up.

§3.1Preseason consensus (attack and defence, independently)

In short: a club's tier from 1 to 5 maps to a ratio from 0.84 to 1.16, where 1.00 is average.

Tier 10.84
Tier 20.92
Tier 31.00
Tier 41.08
Tier 51.16

Bar length is proportional to the ratio (1.16 fills the bar).

consensus = 0.76 + tier * 0.08 // tier in 1..5

data/manual/team-strengths.json holds one overall tier and separate attack and defence tiers (1–5) per club.

  • For a returning club, the attack/defence split comes from its 2025/26 FPL attack/defence strength ratios. The file averages that 50/50 with the overall consensus tier and rounds to the nearest whole tier.
  • A promoted club with no top-flight history uses the overall tier for both. The file's own method field documents this.
  • A club with an overall tier but no separate split uses the overall tier for both attack and defence, not undefined.
  • If no consensus tier exists at all for a dimension, the app uses the raw home/away/attack/defence strengths from the bootstrap payload, and falls back to 1.0 if those are missing.
Why this exact rescale

0.76 + tier * 0.08 is not an arbitrary rescale. It puts tiers 1–5 exactly on 0.84, 0.92, 1.00, 1.08, 1.16. These are the same five anchors that the clean-sheet probability table (§7.4) was calibrated against. A raw 1–5 integer would break every multiplier that assumes "1.0 = average", and it would make nearestStrengthTier (§7.4) snap almost every team to the wrong table row.

consensusRatio applies this to rating (overall), attackRating and defenceRating independently.

§3.2Normalization by source

In short: each value is divided by the league average, and the app never averages hand-set ratios with raw FPL numbers in one pool.

Consensus group

Ratios near 0.84–1.16. Averaged only with each other.

Fallback group

Raw FPL fields, which can run in the hundreds. Averaged only with each other.

Mixed pools would let one club without a manual tier crush every other club's ratio onto its scale. normalizeBySource computes the mean separately in each group, per dimension.

attackHome = attackHome.value / mean(attackHome values from the same source: consensus or fallback) attackAway = attackAway.value / mean(attackAway values from the same source) defenceHome = defenceHome.value / mean(defenceHome values from the same source) defenceAway = defenceAway.value / mean(defenceAway values from the same source) overall = (overallHome + overallAway) / 2, each normalized the same way

Both groups end on the same 1.0-centred scale.

A value above 1.0 means above average in that dimension. The consensus layer does not split by venue, so attackHome and attackAway share one consensus value. Venue enters later as the flat home/away multiplier in §7.1.

§3.3In-season form (Joint Poisson & schedule-adjusted recency-weighted xG)

In short: as matches are played, the app shifts each club's strength toward its own expected-goals record, and the shift grows with every match.

Prior§3.1–3.2 ratio
+
Observedrecent xG for and against, adjusted for opponents
→
Blendedweight on observed = n / (n + 12)

applyInSeasonForm uses expected goals (xG), not goals scored and not win/draw/loss.

The share of this season grows with matches played

12 matches50%
23 matches65.7%
38 matches76%
currentShare = matchesPlayed / (matchesPlayed + 12) blended = prior * (1 - currentShare) + observed * currentShare

Made-up ratios for one club, 12 matches played.

  1. currentShare = 12 / (12 + 12) = 0.5.
  2. Prior 1.10, observed 1.30.
  3. blended = 1.10 * (1 − 0.5) + 1.30 * 0.5 = 0.55 + 0.65 = 1.20.
The Joint Poisson fit (used when fixture opponent data is present)

When completed fixtures carry opponent and venue, applyInSeasonForm fits a Joint Poisson log-linear attack and defence model (fitJointTeamStrengths).

log λ_home = log(x̄G * 1.102) + a_home - d_away log λ_away = log(x̄G * 0.898) + a_away - d_home
  • The parameters a_i and d_i carry an L2 shrinkage penalty toward the zero-centred logarithm of the preseason prior. The prior weight is λ_prior = 12.
  • Each fixture's weight decays by recency with decay = 0.90. The weights scale so that each team's effective sample matches its total appearances.

The fallback: schedule-adjusted weighting (no opponent data)

With no fixture opponent data (for example, synthetic test fixtures), applyInSeasonForm falls back to a heuristic blend, blendInSeasonForm. It adjusts each match for the opponent's prior strength:

adjXgFor_i = xgFor_i * oppPrior.defence adjXgAgainst_i = xgAgainst_i / oppPrior.attack

Attack credit

Creating 1.5 xG against a stout 1.25 defence counts as 1.5 * 1.25 = 1.875. Against an anemic 0.80 defence it counts as 1.5 * 0.80 = 1.20.

Defence credit

Conceding 1.0 xG to a potent 1.25 attack is forgiven down to 1.0 / 1.25 = 0.80. Conceding 1.0 xG to a weak 0.80 attack counts up to 1.0 / 0.80 = 1.25.

Each finished match gets a weight that decays with recency:

Why xG, why this share, and what the data feeds on
  • Why xG. A backtest over 2023/24–2025/26 found that goals and win/draw/loss both do worse than never updating the prior. Goals carry too much finishing luck. Win/draw/loss folds attack and defence into one signal. xG clearly improves clean-sheet prediction (AUC) and the link to actual points.
  • Joint model result. Over 3 seasons the joint model cut player xP RMSE against the heuristic static arm by −0.00258 (95% bootstrap CI [−0.00445, −0.00063]), winning 99.4% of gameweek clusters.
  • Two separate decays. decay = 0.90 sets recency inside the current-season xG estimate. The share of team strength grows on its own as n / (n + 12), so the window's effective sample size does not cap it.
  • No venue split. The blend stays venue-agnostic like the prior. A variant with separate home and away xG streams was tested and rejected: splitting an already thin sample by venue adds noise faster than signal.
  • overall. It comes from the blended attack/defence average, not from a separate consensus number, since nothing downstream scores with overall.
Where the observed xG comes from
  • Once every fixture in a gameweek is finished, loadInSeasonForm.ts sums each player's live expected_goals (event/{gw}/live/) by team. It pairs each fixture's two teams to get xG-for and xG-against, and saves the small total so the app never re-fetches an immutable gameweek.
  • It skips Double Gameweeks. The event feed totals each player's xG over the whole gameweek and cannot split it by fixture.
  • A gameweek whose total is zero across every team counts as unresolved (likely an upstream field rename), not as a cached shutout.

§3.4What a strength number is, and what it is not

In short: every strength value is a ratio around 1.0, and each use divides one by another, so the overall level drops out.

ConsumerExpression
attack multiplier (§7.2)ownAttack / opponentDefence
schedule-adjusted form (§6.3.2)player's past xG / their team's attack
clean sheets (§7.4)attack'_opponent / defence'_own

Illustration (made-up numbers)

Own attack 1.2, opponent defence 0.8

1.2 / 0.8 = 1.5

Every team's strength doubled

Own attack 2.4, opponent defence 1.6

2.4 / 1.6 = 1.5

A ratio cancels the level. Double every team's attack and defence and nothing above changes. So the absolute scale never had to be right, and it is not. The level log(attack) + log(defence) is about 1.7x narrower than an independent Poisson fitted to the same season's xG (sd 0.189 against 0.319 over 2026/27's opening rounds).

Two things compress it. The §3.1 seed spans only 0.84–1.16 by construction, and §3.3 pulls the fit back toward that seed with a prior weight of 12.

RejectedRescaling the level onto the goal scale. Walk-forward on 660 team-fixtures it is monotonically worse on team xG: +0.0100 at 1.35x, +0.0186 at 1.69x, +0.0241 at 2.0x, every paired interval excluding zero. Clean-sheet Brier moves by less than the data can resolve. It also lifts the share of team-fixtures where the §7.2 clamps bite from 16.4% to 43.3%. Using ClubElo for part of the level is worse on the same measure at every weight tested (0.25 to 1.0).

This is why §7.4 carries its own level instead of re-levelling section 3 for everyone. The clean-sheet read needs an absolute goal-scale mean, and the ratios were never built to supply one.
